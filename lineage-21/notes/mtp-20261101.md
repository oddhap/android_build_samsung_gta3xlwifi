# SM-T510 Android 14 USB/MTP candidate

Status: **USB rc physically validated on the October 15 ROM**. Internal storage
enumeration and 16,777,339-byte upload/download tests pass with identical SHA-256,
both with and without ADB. Two ADB/MTP switch cycles pass. The owner rebooted
and accepted macOS USB access; ADB and MTP work after reboot. SELinux remains
Enforcing and file-based encryption remains enabled. Only the USB rc was
installed; the complete offline vendor image has not been flashed.
The October 15 release remains unchanged. A separate November 1 ARM64 ROM now
packages this same USB rc; its offline checks and full-ROM runtime limits are
recorded in `reports/release-20261101/validation-summary.json`.
See `reports/mtp-20261101/validation-summary.json`.

The installed October 15 ARM64 build reproduces the report. `svc usb
setFunctions mtp` starts MtpService but it logs `Couldn't get control FD!` and
`Failed to start usb driver!`. The active configuration can report `mtp,adb`
while host libmtp cannot find the MTP interface/endpoints.

There are two incompatible init owners: the generic system configfs actions
refer to `mtp.gs0`/`ptp.gs1`, whereas Samsung's vendor script creates `mtp.0` /
`ptp.0`, prelinks all functions, and uses Samsung's sysfs function selection.
The kernel also supplies Samsung's `/dev/usb_mtp_gadget` interface instead of
Android's `/dev/mtp_usb` legacy MTP ABI. Renaming a configfs instance or forcing
`mtp,acm,adb` does not resolve the userspace interface.

The candidate replaces `vendor/etc/init/init.exynos7904.usb.rc` with
`lineage-21/configs/init.exynos7904.usb.rc`. It uses FunctionFS for MTP and PTP,
mounts both endpoint sets before system_server opens their control descriptors,
and links only the requested functions. Device-owned `sys.usb.configfs=2`
excludes the generic system actions (which test for 0 or 1), avoiding duplicate
state machines. No kernel, policy permissions, encryption or recovery change
is included. ADB, MTP, PTP, RNDIS, MIDI and Android accessory action sets are
retained; these additional modes still need physical regression testing.

`build-hybrid-vendor.py` applies the replacement on a fresh vendor build with
an exact checksum guard for the original USB script. To prepare a separate
image from the reviewed October 15 sparse ARM64 vendor without rebuilding the
ROM, run on Linux:

```sh
sudo python3 lineage-21/tools/prepare-mtp-vendor.py \
  --input /path/to/reviewed/vendor.img \
  --output /path/to/new/candidate-directory
```

The output directory must not exist. The tool checks all filesystem entries,
contents, owners, modes and xattrs, permits only the USB init file to differ,
and runs read-only e2fsck before generating a separate sparse image and report.
It does not stage a prebuilt or relax the OTA hash guard. A future full ROM
must promote the reviewed candidate vendor hash through device releasetools
and input provenance, use a unique build identity and retain existing signing
keys. The October 15 OTA source guard rejects this replacement image; the November 1
source pins the audited new image with the same exact-checksum mechanism. `stage-arm64-device.py` accepts `--vendor-image` and `--vendor-report` for
isolated inputs. After staging, run `configure-arm64-release.py` **before**
`configure-arm64-verifiers.py --vendor-report /path/to/report.json`: the first
updates existing signer/OTA guards against staged provenance and the previous
input lock, and the second updates the verifier and input lock. All guards
remain exact SHA-256 checks. The reconfiguration regression covers refresh,
idempotence, preservation of the existing recovery/vendor mount safeguards,
and rejection of a staged image inconsistent with its provenance.

Offline checks passed: Android 14 host_init_verifier, Python compilation,
filesystem mutation/metadata audit and e2fsck. Physical acceptance must include
normal file-transfer selection, unlocked storage enumeration, host upload and
download with SHA-256 comparison, return to ADB, repeat mode switches and
reboot persistence under SELinux Enforcing. Those checks have now passed for MTP/ADB on the installed rc. Xubuntu/Thunar
itself and the additional USB modes still need separate confirmation.
The first apparent disconnect was followed by owner approval of USB access in
macOS; subsequent mode switches and transfers passed without an rc revision.

Host round-trip test (creates and deletes only its own test object in Download):

```sh
cc $(pkg-config --cflags libmtp) lineage-21/tests/mtp_roundtrip.c \
  $(pkg-config --libs libmtp) -o /tmp/mtp-roundtrip
/tmp/mtp-roundtrip /path/to/test-payload.bin /path/to/download.bin codex-mtp-test-check.bin
sha256sum /path/to/test-payload.bin /path/to/download.bin
```
